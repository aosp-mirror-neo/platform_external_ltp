VTS LTP Workflow
================

A Guide to Developing LTP for VTS/Android

What is LTP?
------------

[Github](https://github.com/linux-test-project/ltp) (upstream)

LTP (Linux Test Project) is a suite of tests that covers both kernel interfaces
and userspace functionality (glibc, commonly used binaries, etc).  For the
purposes of Android the userspace functionality testing is of less importance
and in fact much of it must be disabled, given the functionality is not
available in Android.

As of 2026, thousands of LTP test cases are executed in VTS across 32-bit and
64-bit targets. Many additional upstream tests exist in the tree but are
disabled in the build or VTS configuration because they test userspace
components or kernel features not applicable to Android.

Submitting Fixes Upstream
--------------------------

The mailing list for LTP is located
[here](https://lists.linux.it/listinfo/ltp) (archived on
[lore.kernel.org/ltp](https://lore.kernel.org/ltp/)). Patches can also be
submitted as pull requests on
[GitHub](https://github.com/linux-test-project/ltp). Standard Linux kernel
guidelines apply: patches should pass `make check` / `scripts/checkpatch.pl`,
follow the LTP C Test API conventions, and be sent in plain text in canonical
patch format (`git format-patch` and `git send-email`).


Landing Fixes in Android
------------------------

**All commits should be pushed to upstream LTP first.** We periodically sync from
upstream to the Android tree.

If you need to land a fix in the Android tree immediately:
1. The change **must** still be submitted upstream first (to the mailing list or
   as a pull request).
2. Import the patch into `external/ltp`:
   * **Merged upstream (`UPSTREAM:`)**: `git cherry-pick -x <sha>` from the
     upstream `master` branch and prefix the original upstream commit subject
     with `UPSTREAM: ` (for example, `UPSTREAM: inode01: ...`).
   * **Pending on the mailing list (`FROMLIST:`)**: Apply the series directly
     from Lore using `b4 shazam <lore_url>` and prefix the original upstream
     commit subject with `FROMLIST: ` (for example, `FROMLIST: swapon04: ...`).
3. Keep the original upstream trailers (including the author's `Signed-off-by:`)
   intact in the upper trailer block, followed by a blank line and the Android
   footer block (`Bug:`, `Link:`, `Test:`, `Change-Id:`, and the importer's
   `Signed-off-by:`).

**Warning:** If you do not follow this process and land code only in the Android
tree, your changes are likely to cause conflicts or be lost during the next
upstream merge/sync.


How is LTP Run in VTS?
----------------------

The LTP source is located at `external/ltp` in the Android tree. While it tracks
upstream closely, a small set of Android-specific build rules, compatibility
headers, and structured patches are maintained locally. In addition to
`external/ltp`, the VTS test configuration generator is located at
`test/vts-testcase/kernel/ltp`. Some noteworthy directories and files:

* `external/ltp/android/`: Contains Android-specific build rules, compatibility
  headers, and helper scripts, aside from `Android.bp` at the top level.
* `external/ltp/gen.bp`: Auto-generated Soong build rules for LTP libraries,
  test binaries (`ltp_<test>`), and prebuilt helper scripts. Generated by
  `android/tools/gen_android_build.sh`.
* `external/ltp/testcases/Android.bp`: Auto-generated `sh_test` rules that
  install LTP test data files and realtime helper scripts under
  `vts_ltp_tests/testcases/`. Generated by `android/tools/gen_android_build.sh`.
  The shared `ltp_defaults` and `ltp_test_defaults` live in the hand-written
  top-level `external/ltp/Android.bp`.
* `external/ltp/android/Android.bp`: Auto-generated Soong rules defining the
  `LTP_TESTS` target list, the `ltp_testcases.zip` archive
  (`ltp_testcases_<target>.zip`, such as `arm64` or `x86_64`), the
  `ltp_config_*` XML generation rules, and the `vts_ltp_test_*` modules.
  Generated by `android/tools/gen_android_build.sh`.
* `external/ltp/android/include/`: Android and Bionic compatibility headers,
  including the manually maintained `config.h`, `bionic-compat.h`, and header
  wrappers (such as `sched.h`).
* `external/ltp/android/tools/disabled_tests.txt`: Lists tests which cannot or
  should not be compiled for Android. Read by `gen_android_build.sh` and
  `gen_ltp_config.py`.
* `external/ltp/patches/`: Contains categorized local patch files (`16K-`,
  `LAPI-`, `LIB-`, `SYS-`) recording Android-specific source modifications.
* `external/ltp/testcases/`: Source for LTP tests. Among the most important for
  Treble/GKI validation are those in `external/ltp/testcases/kernel/syscalls`.
* `test/vts-testcase/kernel/ltp/testcase/tools/configs/disabled_tests.py`:
  Defines `DISABLED_TESTS` (tests excluded from all VTS runs) and
  `DISABLED_TESTS_HWASAN` (tests excluded only on `*_hwasan` configurations).
* `test/vts-testcase/kernel/ltp/testcase/tools/configs/mandatory_tests.py`: Maps
  enabled VTS LTP tests to `True` (mandatory: `TCONF` / exit code 32 is a hard
  failure) or `False` (non-mandatory/skippable: `TCONF` is reported as ignored,
  while `TFAIL`/`TBROK` still fail). Note that older release branches (such as
  `android17-tests-dev`) still use `stable_tests.py`.

Running LTP through atest
-------------------------
You can run LTP tests with atest, which handles all the setup and build steps.

To run all 32 bit LTP tests:
* `atest vts_ltp_test_arm`

To run all 64 bit LTP tests:
* `atest vts_ltp_test_arm_64`

To run a single test:
* `atest vts_ltp_test_arm:dio.dio13_32bit`
* `atest vts_ltp_test_x86_64:syscalls.chdir01_64bit`

Running LTP through VTS
-----------------------
To run VTS LTP it must first be built. VTS is not device specific, you need not
compile it specifically for the device you wish to run it on, assuming it is
the same architecture.

* `. build/envsetup.sh`
* `lunch`
* `make -j vts`

Then open vts-tradefed and run the VTS LTP module:
* `vts-tradefed`
* `vts-tf > run vts-kernel -m vts_ltp_test_arm`

If you regularly work with multiple devices it may be useful to specify the
specific device you wish to run VTS on via the serial number:
* `vts-tf > run vts-kernel -m vts_ltp_test_arm -s 000123456789`

Or a specific test within the module:
* `vts-tf > run vts-kernel -m vts_ltp_test_arm -t dio.dio13_32bit`

Running LTP Directly
--------------------

Running LTP tests within VTS can be quite cumbersome, especially if you are
iterating a lot trying to debug something. You can build a single LTP test
module directly with Soong:

* `m ltp_<test_name>` (for example, `m ltp_swapon04`)

Or build all modules under `external/ltp` and sync them to the device:

* `external/ltp$ mma`
* `external/ltp$ adb sync data`

The test binaries will be located under
`$OUT/data/nativetest{64,}/vts_ltp_tests/testcases/bin` (or pushed to
`/data/local/tmp/vts_ltp_test_<arch>/<target>` when run via TradeFed).

Sometimes you need to perform this step after syncing:
* `external/ltp$ git clean -x -f -d`
Otherwise, build will fail.

To approximate the environment that VTS creates for each test (as defined in
`test/vts-testcase/kernel/ltp/testcase/tools/ltp_test_cases.py`, which sets
`LTPROOT=/data/local/tmp/<module>/<target>`, `PATH=/system/bin:$LTPROOT`, and
`LTP_TIMEOUT_MUL=4` on `lowmem`/`hwasan` configurations), set the following
environment variables before running the binary on the device:

* `adb root && adb shell`

In the root shell on device:
* `mkdir -p /data/local/tmp/ltp/tmp/ltptemp`
* `mkdir -p /data/local/tmp/ltp/tmp/tmpbase`
* `mkdir -p /data/local/tmp/ltp/tmp/tmpdir`
* `chmod -R 777 /data/local/tmp/ltp/tmp`
* `restorecon -F -R /data/local/tmp/ltp`
* `export LTPROOT=/data/local/tmp/ltp`
* `export LTP_DEV_FS_TYPE=ext4`
* `export TMP=$LTPROOT/tmp`
* `export TMPBASE=$TMP/tmpbase`
* `export LTPTMP=$TMP/ltptemp`
* `export TMPDIR=$TMP/tmpdir`
* `export LTP_TIMEOUT_MUL=2`

For running 64-bit tests:
* `export PATH=/system/bin:$LTPROOT:/data/nativetest64/vts_ltp_tests/testcases/bin`

Or for running 32-bit tests:
* `export PATH=/system/bin:$LTPROOT:/data/nativetest/vts_ltp_tests/testcases/bin`

How do I enable or disable tests from the LTP build?
----------------------------------------------------

Tests are disabled from the LTP build by adding them to
`external/ltp/android/tools/disabled_tests.txt` (individual C sources or
binaries) or `external/ltp/android/tools/disabled_libs.txt`. Some tests are not
applicable to Android and therefore should not be built.

To make a change to what is built in LTP, add or remove an entry in
`disabled_tests.txt`, and then regenerate the Android Soong build files:

* `external/ltp/gen.bp`: Soong rules for LTP libraries, test binaries, and
  prebuilt scripts
* `external/ltp/testcases/Android.bp`: `sh_test` rules for LTP test data files
  and realtime helper scripts under `testcases/`
* `external/ltp/android/Android.bp`: `LTP_TESTS` list, `ltp_testcases.zip`, and
  `vts_ltp_test_*` module definitions

Update these files by running
`./android/tools/gen_android_build.sh --update` from `external/ltp` (see
`external/ltp/android/how-to-update.txt`).


How do I enable or disable tests from VTS LTP?
----------------------------------------------

In addition to whether modules are built in `external/ltp`, the VTS
configuration in `test/vts-testcase/kernel/ltp/testcase/tools/configs/` controls
which built tests are executed in VTS and how their exit codes are interpreted:

* `mandatory_tests.py` (`MANDATORY_TESTS`): Dict mapping
  `<suite>.<test>_<32|64>bit` to a boolean:
  * `True`: The test is **mandatory**. Every required kernel feature is expected
    to be present; `TCONF` (exit code 32) is treated as a test failure.
  * `False`: The test is **non-mandatory (skippable)**. Used when a test depends
    on optional kernel configs, hardware capabilities, or kernel versions not
    mandated across all Android devices. `TCONF` (exit code 32) is reported as
    skipped/ignored, whereas `TFAIL` and `TBROK` still fail the test run.
* `disabled_tests.py` (`DISABLED_TESTS` and `DISABLED_TESTS_HWASAN`): Python
  `set`s listing tests excluded from all VTS execution (`DISABLED_TESTS`) or
  excluded only on `*_hwasan` configurations (`DISABLED_TESTS_HWASAN`).

Tests that will never be relevant to Android should be disabled from the build
in `external/ltp` or placed in `disabled_tests.py`. Tests that are temporarily
broken due to an open kernel or test bug should be moved to `disabled_tests.py`
with a `# b/<bug_id>` comment until fixed.

After modifying `mandatory_tests.py` or `disabled_tests.py`, always validate
that formatting is valid, no test appears in both `MANDATORY_TESTS` and
`DISABLED_TESTS`, and the TradeFed XML configs generate cleanly:

```bash
cd test/vts-testcase/kernel/ltp/testcase/tools
python3 test_launcher.py
m ltp_config_x86_64 ltp_config_arm_64
```

If the per-binary timeout of LTP tests needs adjustment, update both
`per-binary-timeout` entries (for the mandatory and skippable `KernelTargetTest`
blocks) in
`test/vts-testcase/kernel/ltp/testcase/tools/template/template.xml`.

recently merged or the build files were recently updated, stale files in
external/ltp can cause build failures.

Testing x86_64
--------------

It is not advisable to run LTP tests directly on your host unless you are fully
aware of what the tests will do and are okay with it. These tests may
destabilize your box or cause data loss. If you need to run tests on an x86
platform and are unsure if they are safe you should run them in emulation, in a
virtualized environment, or on a dedicated development x86 platform.

To run LTP tests for x86 platform, you can do:
* `atest vts_ltp_test_x86`
* `atest vts_ltp_test_x86_64`


Resolving Platform-Specific Assumptions on Android
--------------------------------------------------

Upstream LTP targets standard GNU/Linux distributions (glibc, GNU coreutils,
unencrypted local filesystems, loadable kernel modules). When bringing new or
updated LTP tests to Android, failures often stem from platform-specific
assumptions rather than kernel regressions. Use the following patterns to
diagnose and resolve them:

### 1. Bionic libc vs. glibc Compatibility

* **Manual `config.h` Feature Macros**: Android builds LTP through Soong without
  running autotools `./configure`. When upstream adds `configure.ac` checks and
  fallback definitions in `include/lapi/` for structs or functions that Bionic
  already provides (such as `struct sched_attr`, `struct keyctl_dh_params`,
  `struct prctl_mm_map`, or `tc_pedit` enums), define the corresponding `HAVE_*`
  macros in `android/include/config.h` (or `Android.bp`) to prevent redefinition
  errors.
* **Cross-Release Symbol Versioning (`LIBC_<API>`)**: VTS binaries compiled on
  the `main` branch are also executed against older platform system images (for
  example, in mixed-build GKI testing). When Bionic introduces a syscall wrapper
  in a newer API level (such as `sched_setattr()` and `sched_getattr()` in API
  37), linking against it produces binaries that fail to load on older releases
  (`CANNOT LINK EXECUTABLE`). Hide the Bionic declaration via a header wrapper
  under `android/include/` (for example, `android/include/sched.h`) and leave
  `HAVE_*` undefined in `config.h` so LTP uses the `syscall()`-based fallback in
  `include/lapi/sched.h`.
* **32-bit Bionic Userspace Pointer Wrappers**: Tests that intentionally pass
  unmapped or invalid pointers to verify `EFAULT` (such as `epoll_pwait04`
  passing an invalid `sigmask` pointer) may crash with `SIGSEGV` in 32-bit
  Bionic wrappers that dereference arguments in userspace (for example, to
  convert 32-bit `sigset_t` to `sigset64_t`) before invoking the syscall. Fix
  these upstream by calling the raw syscall via `tst_syscall()`.
* **UAPI Header Sanitizing & Missing Structs**: Bionic's UAPI header generator
  renames C++ keywords (for example, `private` becomes `__linux_private` in
  `struct keyctl_dh_params`, so code must use the upstream `priv` union alias),
  and Bionic omits some legacy glibc headers/structs (such as `elf_prstatus` in
  `<sys/procfs.h>`). Upstream fixes using `configure.ac` field detection or
  `include/lapi/` fallback definitions are preferred over local hacks.

### 2. Filesystem, Encryption (FBE), and SELinux Policies

* **File-Based Encryption (`fscrypt`) on `/data/local/tmp`**: On Android,
  `/data/local/tmp` resides on an FBE-encrypted filesystem. Kernel interfaces
  that reject `fscrypt`-encrypted files (such as `swapon()` returning `EINVAL`
  on encrypted swapfiles) must allocate their backing files inside a mounted
  loop device filesystem (`.mount_device = 1` with `.mntpoint`, optionally
  combined with `.all_filesystems = 1`) rather than directly under `$TMPDIR`.
* **SELinux Enforcement on Unlabeled Loop Backing Files**: On kernels prior to
  v6.15 (without commit `f2fed441c69b`, "loop: stop using vfs_iter_{read,write}
  for buffered I/O"), loop worker kernel threads access backing files using the
  `u:r:kernel:s0` domain. Under Android's enforcing SELinux policy, the kernel
  domain is denied access to unlabeled files created on freshly formatted test
  filesystems, causing loop I/O to fail with `EIO` (for example, in `swapon04`).
  Tests should probe loop device I/O in `setup()` and report `TCONF` when
  blocked by LSM policy.
* **Asynchronous Loop Device Node Creation**: In virtualized Android
  environments (Cuttlefish/AVD), `/dev/loopX` device nodes may appear
  asynchronously after `LOOP_CTL_GET_FREE` returns. LTP library helpers in
  `lib/tst_device.c` use exponential backoff polling when opening or statting
  newly allocated loop devices.

### 3. 16KB Page Size Compatibility

* Android supports both 4KB and 16KB page sizes, as well as x86_64 16KB page
  size emulation. Tests must not hardcode `4096` for memory mappings, fault
  granularity, signal alternate stacks, or pipe buffer calculations.
* Query page size dynamically via `getpagesize()` / `sysconf(_SC_PAGESIZE)`, or
  use `kernel_page_size()` from `include/pgsize_helpers.h`
  (`patches/16K-*.patch`) when a test specifically inspects kernel-level VMA or
  pagemap granularity on emulated 16KB targets.

### 4. Android Userspace & GKI Kernel Architecture

* **Built-in GKI Features & Module Paths**: Android GKI kernels build core
  subsystems in-tree and place loadable kernel modules under
  `/vendor/lib/modules` or `/system/lib/modules` (`vendor_dlkm` / `system_dlkm`)
  rather than `/lib/modules/$(uname -r)`. Tests that unconditionally invoke
  `modprobe` fail unless upstreamed to check whether the feature is already
  built-in. Tests for optional kernel features or hardware drivers that
  legitimately return `TCONF` (exit code 32) on unsupported devices should be
  configured as non-mandatory (`False`) in `mandatory_tests.py`.
* **Userspace Daemons & Toybox Utilities**: Android does not run traditional
  distro daemons (such as userspace `irqbalance`, so tests like `irqbalance01`
  that only inspect userspace IRQ distribution are disabled in
  `disabled_tests.py`, see b/571822610) and provides Toybox instead of GNU
  coreutils. Shell-based LTP tests should stick to POSIX options, and
  `template.xml` automatically rewrites `#!/bin/sh` and `#!/bin/bash` shebangs
  to `#!/system/bin/sh` during test preparation.


Upgrade LTP source code
-----------------------

While the official LTP releases from upstream are quarterly (see [GitHub releases](https://github.com/linux-test-project/ltp/releases)), the `external/ltp` project in Android is configured to track upstream master branch commits (commit-by-commit) to ensure more regular, often monthly, updates within Android.

The `platform/external/ltp` project has a tracking branch `upstream-master` (https://android.googlesource.com/platform/external/ltp/+/refs/heads/upstream-master) that mirrors changes from upstream [github.com/linux-test-project/ltp](https://github.com/linux-test-project/ltp).

### Automatic Upgrade (Recommended)

To upgrade LTP to the latest upstream commit and automatically regenerate
Android build files, run the following command from your Android checkout root (`$ANDROID_BUILD_TOP`):

```bash
tools/external_updater/updater.sh update --no-upload --keep-local-changes external/ltp
```

This tool will automatically:
1. Fetch the latest commits from the upstream repository.
2. Merge the changes into the local branch.
3. Trigger the post-update hook (`post_update.sh`) which:
   - Restores Android-specific files and custom runlists during upgrades.
   - Automatically runs the Soong blueprint generator (`gen_android_build.sh`)
     to regenerate `Android.bp` files (requires Docker under the hood; see `go/docker` for rootless setup).
4. Create a Git commit with the upgrade.

*(Note: If blueprint regeneration is skipped in non-interactive environments due to Docker permissions, run `cd android/tools && ./gen_android_build.sh --update` manually afterward).*

### Manual Upgrade

If you need to manually perform the upgrade without using `external_updater`, follow these steps:

1. Sync the upstream tracking branch:
   ```bash
   repo sync .
   ```
2. Create a new branch to work on the merge:
   ```bash
   repo start mymerge .
   ```
3. Find the latest commit or release from the upstream tracking branch (`goog/upstream-master`):
   ```bash
   git log --oneline goog/upstream-master
   ```
4. Merge the upstream commit:
   ```bash
   git merge <upstream commit> --no-ff
   ```
5. Resolve any merge conflicts, verifying the build with:
   ```bash
   git clean -dfx && make autotools && ./configure && make -j
   ```
6. Regenerate Android build targets manually using the helper script:
   ```bash
   git clean -dfx && ./android/tools/gen_android_build.sh --update && git clean -dfx && mma
   ```

### Manual Verification

After upgrading (via either method), verify the build and run tests:
1. Build LTP: `mma` (from `external/ltp`).
2. Run tests: `atest vts_ltp_test_arm` or `atest vts_ltp_test_arm_64`.

### Writing the Commit Message (Comparing Test Suites)

It is good practice to write a detailed commit message presenting the differences (added/removed tests) in the new LTP version. 

You can use the helper script `android/tools/compare_ltp_projects.py` to
compare the tests of two LTP versions. Each side of the comparison can be
given in one of three ways:

| Input | Options | What is read |
|---|---|---|
| Git revision | `--old-rev REV`, `--new-rev REV` | `runtest/` as committed in `REV`. `REV` is anything git understands: a SHA, `goog/main`, `HEAD~1`, `<sha>^1`, ... It is resolved in the `external/ltp` repository that contains the script, or in the repository given with `--git-repo DIR`. |
| Directory | `--ltp-old DIR`, `--ltp-new DIR` | `DIR/runtest/` as it is on disk, including uncommitted changes. |
| JSON file | `--ltp-old-json FILE`, `--ltp-new-json FILE` | A snapshot written by an earlier run (see "Two steps" below). |

Any combination of old and new inputs works:

| Old | New | Command | Compares |
|---|---|---|---|
| revision | directory | `--old-rev goog/main --ltp-new .` | `goog/main` with the working tree. Use this while the update is applied but not committed yet. |
| revision | revision | `--old-rev <sha>^1 --new-rev <sha>` | The parent of an update commit with the update commit. |
| directory | revision | `--ltp-old /tmp/ltp_old --new-rev HEAD` | A directory with a commit. |
| directory | directory | `--ltp-old /tmp/ltp_old --ltp-new .` | Two directories. `post_update.sh` runs this for archive updates; for git merge updates it runs `--git-repo <project> --old-rev HEAD~1 --ltp-new <project>`. |
| JSON | revision or directory | `--ltp-old-json old.json --ltp-new .` | A saved snapshot with the current tree. |
| one side only | - | `--old-rev goog/main --ltp-old-json old.json` | Nothing. The tool writes the snapshot of that side to the JSON file instead. |
| revision in another checkout | revision | `--git-repo ~/other/ltp --old-rev HEAD~1 --new-rev HEAD` | Two commits of another LTP checkout. `--git-repo` applies to both `--old-rev` and `--new-rev`. |

```bash
cd $ANDROID_BUILD_TOP/external/ltp

# Most common: the update is in the working tree, compare it with goog/main.
android/tools/compare_ltp_projects.py --old-rev goog/main --ltp-new .

# The update is already committed as <sha>.
android/tools/compare_ltp_projects.py --old-rev <sha>^1 --new-rev <sha>

# Two steps: save a snapshot first, compare later.
android/tools/compare_ltp_projects.py --old-rev goog/main --ltp-old-json /tmp/ltp_old.json
android/tools/compare_ltp_projects.py --ltp-old-json /tmp/ltp_old.json --ltp-new .

# Resolve the revisions in another LTP checkout.
android/tools/compare_ltp_projects.py --git-repo ~/other/ltp --old-rev HEAD~1 --new-rev HEAD
```

Notes:

- `--old-rev` cannot be combined with `--ltp-old`, and `--new-rev` cannot be
  combined with `--ltp-new`.
- `--git-repo DIR` can be any directory inside a git checkout; the root of
  the checkout is used. Bare repositories are not supported. The option is
  only accepted together with `--old-rev` or `--new-rev`. It changes where
  revisions are resolved; directories and JSON files are read as before.
- For each side, a revision or directory is used first. If neither is given,
  the JSON file is used. The JSON options default to `ltp_old.json` and
  `ltp_new.json` in the current directory, so an old file with one of these
  names is picked up automatically. Pass explicit paths to avoid surprises.
- A revision reads committed content only. To include uncommitted changes,
  use a directory, for example `--ltp-new .`.
- `external/ltp` is a partial clone. For old revisions, git may have to
  download files first. This needs a valid SSO certificate (`gcert`).
- Upstream release tags such as `20260930` are not available in this
  repository. Use the commit SHA, `goog/main`, or `<sha>^1`.
- For each revision, the script prints the resolved commit SHA on stderr. The
  report itself is printed on stdout, so redirecting or pasting it gives you
  the report only.
